## 1. 作業概要

本プロジェクトでは、タシケントを対象地域としたレストラン口コミ Web アプリケーション **Taomchi** を、Next.js 16 App Router および PostgreSQL を基盤として設計・実装・デプロイした。

英語・ウズベク語・ロシア語・日本語の 4 言語 UI、メール認証、ユーザー投稿型レビュー、管理者向け CRUD 機能、Vercel + Neon + Vercel Blob による本番運用環境の構築を一貫して担当した。

## 2. 完了した作業

### 2.1 基盤・設計

- Next.js 16 App Router + TypeScript プロジェクト構成
- Tailwind CSS v4、shadcn/ui による UI コンポーネント基盤
- Prisma スキーマ設計（6 モデル：User, Category, Restaurant, RestaurantImage, Review, ReviewImage）
- 3 回のデータベースマイグレーション実行（`prisma/migrations/`）
- シードデータ整備（12 レストラン、8 カテゴリ、20 レビュー、4 ユーザー）

### 2.2 認証・セキュリティ

- Auth.js（next-auth v5 beta）Credentials プロバイダーによる登録・ログイン
- bcrypt（コスト 12）によるパスワードハッシュ
- JWT セッション戦略（`AUTH_SECRET` で署名）
- Middleware + `requireAuth()` + `requireAdmin()` による二重ルート保護
- ロールベースアクセス制御（USER / ADMIN）
- `passwordHash` を通常の Prisma クライアントから除外する設計
- プロフィール更新時のセッションリアルタイム反映（`unstable_update`）

### 2.3 公開機能（ゲスト含む）

- ホーム画面：ヒーロー検索、カテゴリグリッド、高評価レストラン、新着レストラン、特長セクション
- レストラン一覧：キーワード検索、カテゴリ・都市・評価・価格帯フィルタ、ソート、グリッド／リスト切替、ロードモア
- レストラン詳細：ギャラリーカルーセル（メイン＋最大 8 枚）、情報カード（住所・電話・営業時間・価格帯）、評価ショーケース（Guest favorite バッジ）
- 404 ページ、エラーバウンダリ、Open Graph メタデータ、動的 favicon

### 2.4 レビュー・プロフィール機能

- レビュー作成（評価 1〜5 点、タイトル、本文、来店日、写真最大 4 枚）
- 自分のレビューの編集・削除（インラインダイアログ、確認ステップ）
- サーバー側権限チェック（他ユーザーのレビューを保護）
- プロフィールページ（統計：総レビュー数・平均評価、登録日）
- プロフィール編集モーダル（氏名・言語設定・ヘッドライン・アバター画像）

### 2.5 管理画面機能

- 管理ダッシュボード（KPI：店舗数・公開数・ユーザー数・レビュー数・平均評価、最近の活動）
- レストラン管理：一覧・作成・編集（多言語フィールド・座標・公開制御・画像）・削除
- カテゴリ管理：4 言語名称の CRUD
- レビュー管理：検索・フィルタ・編集・削除
- ユーザー管理：ロール変更（USER ↔ ADMIN）、アカウント有効化／無効化
- 管理者の自己無効化・降格をサーバー側でブロック

### 2.6 多言語化

- next-intl 4.x による EN / UZ / RU / JA の 4 言語対応
- URL ロケールプレフィックス（`/en/`, `/uz/`, `/ru/`, `/ja/`）
- ヘッダー内言語スイッチャー
- 翻訳 JSON の 4 ファイル（`messages/en.json` 等）に全主要 UI テキストを収録

### 2.7 画像アップロード

- `/api/uploads` エンドポイント（POST / DELETE）
- サーバー側バリデーション（JPEG / PNG / WebP のみ、最大 5 MB、空ファイル拒否）
- 本番：**Vercel Blob** による CDN 配信（OIDC 自動認証対応）
- 開発：ローカル `public/uploads/` への保存
- フォルダ別権限制御（review・avatar：全ログインユーザー / restaurant 系：ADMIN のみ）

### 2.8 テスト・品質

- Vitest 単体テスト 21 ケース（全 Pass）
- Playwright E2E テスト 19 ケース実装（3 ケース自動 Pass、主要フロー手動確認済み）
- TypeScript 型チェック・ESLint・本番ビルド：いずれも成功
- テスト仕様書・実施結果報告書の作成

### 2.9 デプロイ・運用

- Vercel プロジェクト設定（`vercel.json`、ビルドコマンド）
- Neon PostgreSQL（本番）への接続・マイグレーション実行

## 3. 困難だった点と解決策

### 3.1 画像ストレージの選定

**困難：** 当初 Cloudinary を画像ストレージとして設計・実装したが、ウズベキスタン国内ではサービスが利用できないことが判明した。

**解決：** `@vercel/blob` に切り替え（git commit `96b431b`）。Vercel との密な統合により設定が簡素化され、OIDC による自動認証も実現した（commit `d0c4090`）。

### 3.2 Next.js Middleware と Auth.js・next-intl の共存

**困難：** エッジ Middleware で Auth.js によるルート保護と next-intl によるロケール解析を同時に行う必要があり、実行順序と型の整合に時間を要した。

**解決：** `auth.config.ts`（Prisma を含まないエッジ安全版）と `auth.ts`（Prisma 含む完全版）を分離。Middleware は軽量な `auth.config.ts` のみを参照する構成とした。

### 3.3 E2E テストの安定性

**困難：** クライアントサイドルーターによる URL 非同期更新、フォームのハイドレーション前 submit、Playwright ストリクトモードでの複数要素マッチが原因で多数のテストが不安定になった。

**解決：** 権限・バリデーションなどコアロジックを Vitest 単体テストで確実に担保。E2E は手動確認で補完し、原因分析とともに結果報告書に明記した。

### 3.4 プロフィール更新のセッション反映

**困難：** プロフィールの氏名を変更しても、ヘッダーに即時反映されなかった。

**解決：** Auth.js の `unstable_update` を使用して JWT トークン内容をページリロードなしに即時更新する仕組みを実装した（commit `f403e40`）。

### 3.5 デモ画像の確保

**困難：** 外部 URL（Unsplash）を直接参照すると CDN 制限で 404 が発生するケースがあった。

**解決：** `scripts/download-restaurant-images.mjs` で検証済みの画像を `public/images/restaurants/` にダウンロードし、ローカルから配信する方式に切り替えた。

## 4. 学んだこと

1. **サーバー優先設計の効果** — Server Components と Server Actions を早期に採用したことで、データ取得・権限チェック・バリデーションをサーバー側に集約でき、クライアントのコードを簡潔に保てた。

2. **i18n は設計初期から** — 後から翻訳キーを追加するより、`messages/` 構造とロケールルーティングを初期設計から組み込む方が一貫性を保ちやすかった。

3. **テストピラミッドの実践** — E2E だけに頼らず、ビジネスロジック（権限・バリデーション・計算）を Vitest 単体テストで固めることで、E2E が不安定でも品質を担保できた。

4. **本番を見据えた環境分離** — 画像ストレージ（`isUploadStorageAvailable()`）と DB 接続（プール URL / 直接 URL）を開発初期から環境別に設計しておくことの重要性を体得した。

5. **誠実なテスト報告** — 自動テストが未 Pass であることを結果報告書に明記し、原因を分析して記載することが、大学提出における誠実さと技術力の証明につながる。
